From TaleSpark to Fibonacci: audit, direction and roadmap

A planning document. Nothing in the application has been changed. It is based on a read of the code in wizetale-app, wizetale-api and supabase, the project docs, the 20 October 2026 verification report, and a short web search on competitors.

Prepared 20 Oct 2026 · Labels: Found what the code or research shows · Proposal what I recommend · Risk something to act on

02Refined product vision

Proposal Here is where I would push back on the brief.

"Understand information from any source" describes NotebookLM. Google gives it away free and has been adding to it all year, with video overviews and a Sources / Chat / Studio layout. Fibonacci can't win by supporting more file types or listing more outputs. It needs to do one thing NotebookLM doesn't.

My recommendation: Fibonacci makes a path through your material. Chat tools wait for you to know what to ask. Fibonacci reads the source, finds the ideas, puts them in the order they build on each other, and walks you through them. Each step explains one idea, shows the passage it comes from, and checks that you understood before moving on. The name fits literally: each step builds on the ones before it.

Positioning

Fibonacci turns the material you have to learn into a path you can follow, with every step traced to its source.

Who it is for (first)

  • Primary: students aged 15–22 learning from material someone gave them, like a textbook chapter, lecture recording or assigned article, who need to understand it for an exam or assignment.
  • Secondary: teachers who turn their own material into lessons and practice. The existing teacher mode does this already, so the engine is shared.
  • Later: independent learners and professionals working through papers, reports or courses.

The current 10–18 audience brings parental-consent and child-safety obligations that block a public launch. Whether to keep it is your decision; see section 12.

What Fibonacci is not

  • Not a general chatbot. If the sources don't say something, Fibonacci says so, then offers to explain from general knowledge, clearly labelled.
  • Not a video generator first. Video is one output, and the most expensive one.
  • Not a public library. Sources stay private to the user.

Where Fibonacci can be different

  1. The path. Ideas in the order they depend on each other, with "you need X before Y" made visible. None of the products above do this.
  2. Each sentence is labelled. Every sentence in an answer is marked as coming from your source (with a page, paragraph or timestamp) or as Fibonacci's own explanation. NotebookLM cites, but doesn't separate explanation from evidence.
  3. Explanations in layers. Each idea has a plain version, a precise version, and a worked example. The learner moves between them.
  4. It tracks understanding. Short checks give each idea a status: new, shaky or understood. The overview shows that status, so the product remembers what you learned, not only what you generated.
  5. Russian and Kazakh at the same quality as English. Kazakh is a real gap in the market. Fonts, prompts and tests for all three languages already exist.
  6. Outputs you can edit. Every output can be edited, saved and printed, which this codebase already does well.

Deliberately cut or deferred, and why

  • Whole books. 200 pages already covers a textbook chapter. Whole books raise cost and copyright questions for little benefit. Ask the user to choose chapters.
  • Video of a whole source in the MVP. It takes minutes per render and costs the most of anything. Concept-sized videos in V1 are more useful and cheaper.
  • Public sharing of projects. It would republish copyrighted source text. Wait for a clear policy.
  • A free-form chat tab. "Ask" lives inside the workspace with the source alongside, not as a separate chat product.

05Complete user journey

Proposal The brief's flow was Landing → Create project → Add source → Analyze → Explore → Generate → Export. I would remove "Create project". Nobody arrives wanting a project; they arrive with a chapter. The source is the first action, and the project is created around it and named after the source.

  1. Arrive. The hero has one field: "Paste a link or add a file". Next to it is a link to a real sample project.
  2. Add a source. The URL or file is checked in the browser right away: type, size, URL format. Problems show inline, like "This PDF is 340 pages. Fibonacci reads up to 200; choose a chapter range."
  3. Sign in, only when needed. The pending source is kept in session storage and resumes after sign-in, which can be Google or email. Nothing is processed anonymously because each job costs money.
  4. Watch it read. Named stages: Reading 48 pages → Finding the ideas → Ordering the path → Ready. The overview appears as soon as it's ready, and the path fills in after. A typical chapter should be done in under 90 seconds. The user can leave and is notified in the app when it finishes.
  5. Get oriented. The workspace opens on the overview: what the material is about, how many ideas it has, about how long the path will take, and a single action: Start with idea 1.
  6. Follow the path. Each idea shows a plain explanation, the passages it comes from, then one check question. Answering marks it understood or shaky and moves on.
  7. Ask at any point. The Ask bar is always at the bottom. Answers label each sentence as from the source or explanation. Clicking a citation opens the source at that page or timestamp.
  8. Make something. The "Make" panel offers a study guide, flashcards or a quiz, scoped to the whole project or to the shaky ideas only.
  9. Come back. The library shows each project with its path progress, like "7 of 12 understood". Returning lands on "Continue: idea 8".

07UI/UX strategy

Principles

  1. One obvious next step on every screen. Landing: add a source. Library: continue or add. Workspace: the next idea.
  2. The evidence is always one click away. Each claim links to its passage. The source viewer opens beside the explanation, never on another page.
  3. Show progress, not spinners. Long jobs show named stages and partial results.
  4. Show advanced options when they're needed. Output settings (count, difficulty, scope) stay hidden until "Make" is opened.
  5. Keep it calm. Animation explains state changes only, like a path step filling in or a citation highlight. No decoration.

The workspace (the most important screen)

NotebookLM uses three equal columns. Fibonacci puts the path in the centre, with the source as a pane that opens beside it when needed. The source sits behind the learning, never in front of it.

How evidence and explanation are shown

Highlighted text = stated in your sourcedashed italic = Fibonacci's explanationp. 241 = citation, opens the passage

The Calvin cycle uses ATP and NADPH from the light reactions to fix carbon dioxide into sugar p. 241. It takes place in the stroma of the chloroplast p. 240.

You can think of the light reactions as charging batteries, and the Calvin cycle as the machine that spends them.

Example content, adapted from OpenStax Biology 2e (CC BY 4.0) for illustration

Colour is never the only signal. Source sentences also have a citation chip, and explanation sentences are italic. Screen readers hear "From source, page 241" or "Explanation".

Other screens

  • Library: a list, not a card grid. Each row shows title, source types, path progress as a small seedhead (section 08), and last opened. The primary action is "Add a source".
  • Source management: inside the workspace rail. Each source shows status (reading, ready, failed with reason), can be renamed or removed, and can be excluded from answers.
  • Make: a panel listing the output types, each with one sentence on what you get. Settings stay folded away. Results open in the existing editors.
  • Video: appears under Make as "Explain this idea as a video". It shows an estimated time and only starts after the user confirms, as the current flow already does.
  • Settings: one page with account, interface language, material language, theme, usage, and delete account.

Accessibility targets

WCAG 2.2 AA. 44px minimum targets. Visible 3px focus rings, as today. Every path state shown by shape as well as colour (filled, half and empty dots). aria-live for job stages. Full keyboard support in the workspace: j/k move through ideas, / focuses Ask, Esc closes the source pane. Reduced-motion turns off all animation.

08Three brand directions

Proposal One constraint applies to all three: every typeface must cover Kazakh Cyrillic (Ә Ғ Қ Ң Ө Ұ Ү Һ І). Coverage must be confirmed by rendering a test page before committing. Golos Text is already confirmed, so it stays as the interface face in the recommended direction.

All three use a Fibonacci spacing scale (3, 5, 8, 13, 21, 34, 55, 89px) instead of the current 4/8 grid. This page uses it too. It is the subtlest way to make the name part of the system.

A · Golden Grid

precise, technical

Concept: mathematical precision and nothing else. A Swiss-style grid with columns at a 1 : 1.618 ratio. The brand is the tiling of Fibonacci squares, never the spiral.

  • Type: Onest (Cyrillic, neo-grotesque) for display and UI, JetBrains Mono for citations and numbers.
  • Layout: strict golden-ratio splits, wide margins, numbered sections that reflect real order.
  • Logo: the 8-5-3-2-1-1 tiling with the smallest square filled cobalt, meaning "where you are".

B · Seedhead

Recommended

Concept: patterns in nature, used as data. A sunflower places each seed 137.5° from the last, which is the golden angle. In Fibonacci, each idea in a path is a seed. The seedhead is the logo, the loading animation and the progress display. Seeds fill in as you understand them. It is the one visual idea in this plan that both means something and does a job.

  • Colour roles: Leaf for actions, Pollen for "understood" and focus (never a button colour), River only for source evidence, so blue always means "from your material". The ground is a cool green-white, not cream. That moves away from the current paper look and the overused cream-and-terracotta style.

Mobile

The hero stacks: headline, field (full width, with a separate "Add file" button because phones can't drag and drop), sample link, then the seedhead and source, cut down to 3 highlighted sentences. The sample tabs become a segmented control. Body text is at least 16px so iOS doesn't zoom into the field.

Accessibility

The field has a visible label. Errors are announced and linked with aria-describedby. The file input is a real button that works from the keyboard. The seedhead has a text alternative ("12 ideas found on this page"). Contrast is checked for both themes. Heading order runs h1 → h2 for each section.

Why this should convert

A visitor sees what Fibonacci does (the hero animation), tries it with no account (the sample), learns why to trust it (section 4), and starts with the same field they already saw. Each section answers one of the four questions in the brief: what it does, why it is useful, how to begin, and what you get.

Segments: about 350 words with a 50-word overlap for documents, or 45-second windows for transcripts. Never split across a page boundary, so citations stay exact. Store content_hash so re-uploading the same file reuses the previous analysis.

Retrieval: start simple

Proposal A typical MVP project, one chapter or about 30k words, fits in a Gemini context window many times over. So:

  1. Small projects (up to about 150k tokens): no retrieval. Send every segment with its ID, and use Gemini context caching so repeated questions are cheap. This is the most accurate option and adds no new infrastructure.
  2. Large projects: the existing Postgres full-text search, plus (V1) pgvector embeddings in the same Supabase database, combined with reciprocal rank fusion. Embedding quality for Kazakh must be tested before adopting it.

This avoids adding a vector database and builds on what exists.

Citations and hallucination control

  1. Each segment goes into the prompt with an ID like [S41]. The model must return structured JSON: sentences: [{text, kind: "source"|"explanation", segment_ids}].
  2. The server checks that every cited ID was in the prompt, as validate_grounded already does but per sentence. For "source" sentences it also runs a cheap check that the key terms appear in the cited segment. A sentence that fails is relabelled as "explanation" or dropped, never shown as evidence.
  3. When nothing relevant is found, the reply is "not in your sources" and no answer is generated.
  4. Evaluation set before launch: 30 questions per language over 3 real sources, including 10 the sources can't answer. Targets: at least 90% citation precision, and the model declines unanswerable questions at least 90% of the time. Run it in CI against recorded responses, and live before each model change.

Analysis job (the path)

Map, then reduce. Each group of about 20k tokens of segments yields candidate ideas with segment IDs. A reduce step merges duplicates and builds the "depends on" links, then orders the ideas topologically, falling back to source order when links are uncertain. Explanations and checks are generated lazily when an idea is first opened, not all up front. That halves analysis time and cost.

Background processing

  • Split the Celery queues: ingest (concurrency 3), analysis (concurrency 2) and render (concurrency 1). This needs a second worker service in Compose, with no new infrastructure.
  • Status: a stage field on the source or job, polled every 1.5 seconds through the existing proxy. Server-sent events can come later; polling works through Vercel and Nginx today without changes.
  • Limits: the 60-second ingestion time limit rises to about 180 seconds for PDFs. A per-job token budget and a per-user daily budget are tracked in Redis, the same pattern as the existing rate limiter.

Security and privacy

  • SSRF: resolve DNS, block private, loopback, link-local and metadata IP ranges, re-check every redirect (5 max), allow only http and https on ports 80 and 443, allow only text/HTML and PDF content types, 10 MB and 15-second caps. Test each of these.
  • Prompt injection from sources: source text is wrapped in delimiters and labelled as untrusted data. The model has no tools or side effects while reading sources. Output is schema-constrained JSON rendered as text (never as HTML). Links in output come only from source metadata. Include injection examples in the evaluation set.
  • Uploads: the existing size limits, zip-bomb check and parser-log suppression stay. Files are stored privately and served only through the authenticated proxy, as today.
  • Privacy: sources are private by default and never shared. Production already requires Gemini's paid tier; the privacy notice should state the provider's data-use terms.
  • Copyright: users add material for their own study. Fibonacci doesn't republish source text, the sample uses openly licensed content, and there is a takedown contact. Have a lawyer confirm this before public launch.

Cost

Gemini Flash-Lite is the right default. Rough cost per typical project: analysis about 40k input tokens, each question about 30k tokens (mostly cached), each output 10–20k. That should come to a few cents per project at current list prices, which need checking. A video render costs more than everything else combined, which is why it is opt-in and limited to one idea. Usage is logged per job (usage_context already exists) so real numbers replace these estimates within the first week.

12Risks and open decisions

Decisions I need from you

1. Who is it for at launch?My recommendation is students aged 15 and up (exam prep, university) and teachers, instead of 10–18. Keeping under-16s means parental consent, age checks and child-safety processes before launch, which are open gates today.
2. Can you use the name "Fibonacci"?It is a common name, and many companies and products use it. Check the trademark in your target countries and confirm which domain you can get before spending on brand work. This is the largest non-technical risk.
3. Brand direction:B (Seedhead) recommended, or A or C?
4. Positioning:Do you agree that "a path through your material" is the core, with video demoted to one output? Or is video central to what you want?
5. Teacher mode:Should it merge into projects (recommended, Phase 6) or stay a separate product?
6. Languages at launch:EN, RU and KK, all to the same evaluation standard? Each language adds evaluation and copy work.
7. Budget:What monthly AI and API spend is acceptable, including a paid YouTube transcript provider? Will there be a free tier, and with what limits?
8. Existing users and data:Is TaleSpark live with real users? If so, data must be migrated and users told about the change. If not, the migration can be simpler.
